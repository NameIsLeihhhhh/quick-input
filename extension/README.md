# DSH Quick Bridge

把 QuickInput 浮层里输入的内容，送进 DSH 的新会话。**不切窗口、不抢焦点、不动剪贴板。**

配 QuickInput 用：QuickInput 负责「呼出 + 拿内容」，本扩展负责「在 DSH 页面里把内容发出去」。

---

## 装（一次性，约 1 分钟）

1. 打开 Chrome 或 Edge，地址栏输入 `chrome://extensions`（Edge 是 `edge://extensions`）
2. 右上角打开 **开发者模式**
3. 点 **加载已解压的扩展程序**，选中这个文件夹 `dsh-quick-bridge`
4. 装好后，把已经开着的 DSH 标签页 **刷新一次**（`F5`）
   —— 让内容脚本注入进去。以后不用再刷。

装完浏览器工具栏会多一个图标，点开就是状态面板。

---

## 验（两下点击，不用碰热键）

点扩展图标，面板里：

| 按钮 | 作用 | 期望结果 |
|---|---|---|
| **发一条测试** | 走完整投递链路 | 显示「✔ 成功」，DSH 里冒出这个新会话 |
| **探测页面** | 报告页面里输入框和「新会话」按钮的识别情况 | 两行都识别到了 |

**先点「探测页面」。** 它输出的是我写代码时看不到的东西：

- `输入框：TEXTAREA（value 字段）` 或 `DIV（contenteditable）` 之类
- `新会话按钮：「＋ 新会话」` 或 `没找到 ✘`

两个都识别到了，就等于成功了大半。有 `✘`，把那两行发我，我按实际情况改选择器。

## 用

1. 任意软件里按 **Alt+Q**
2. 输入内容，回车
3. 浮层消失，**当前窗口不动**
4. 切到 DSH —— 新会话里已经是你刚才那句话

浮层左下角会实时显示桥的状态：

- 绿字 `→ DSH 新会话 · 扩展已连接` = 扩展在线，内容会立刻送出去
- 橙字 `⚠ 扩展未连接，内容先排队` = 扩展没跑或 DSH 标签页没有；内容不会丢，等扩展上线自动补发（排队上限 10 分钟）

---

## 出问题看哪里

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 浮层一直显示「扩展未连接」 | 扩展没装 / 没启动 / DSH 标签页没开 | 开 `chrome://extensions` 看它是启用状态；开一个 DSH 标签页 |
| 面板显示「投递失败：找不到输入框」 | DSH 改版，输入框选择器失效 | 点「探测页面」把输出发我 |
| 面板显示「投递失败：填字失败」 | 输入框是富文本编辑器，三种写入策略都没进去 | 同上 |
| 文字进了输入框但没发出去 | 发送按钮/回车都没触发 | 文字不会丢，切过去按一下回车即可 |
| 浏览器重启后不工作了 | service worker 被回收 | 打开一次扩展图标，或等 1 分钟看门狗自动唤醒 |

日志：QuickInput 的日志在 `%TEMP%\quickinput.log`，每次投递会写一行 `DoSend -> bridge`。

## 技术结构

```
QuickInput.exe ──POST/Push──▶ 127.0.0.1:47321（本地队列，10 分钟过期）
                                        │
                                 GET /poll（每 700ms）
                                        ▼
                          background.js（service worker）
                                        │ chrome.tabs.sendMessage
                                        ▼
                          content.js（在 DSH 页面里）
                                        │
                   点「新会话」→ 填字 → 发送 → 回报 /ack
```

**为什么走本地端口而不是别的**：浏览器扩展不能读写任意文件，也不能访问剪贴板（无用户手势时）。回环端口是唯一干净的通道，且 `127.0.0.1` 天然不对外暴露。

**为什么能操作后台标签页**：content script 在后台标签页里照常运行，DOM 事件、`click()`、`input` 事件全部有效。唯一不能用的是 `requestAnimationFrame`（被节流），所以代码里全用 `setTimeout`。

**填字的三种策略**（逐个试，读到内容才停）：

1. `ClipboardEvent('paste')` + `DataTransfer` —— 富文本编辑器（ProseMirror/Lexical/Slate）都认这个
2. `document.execCommand('insertText')` —— 传统 contenteditable
3. 原生 `value` setter + `input` 事件 —— React 受控的 `textarea`/`input`
4. `textContent` + `input` 事件 —— 兜底

**发送的三种策略**：点发送按钮 → 派发 Enter keydown → 再点一次。

## 已知边界

- 只支持 **Chrome / Edge**（MV3）。Firefox 需要改 manifest。
- DSH 标签页会被自动创建为**后台标签页**，但浏览器可能会把它标成「已丢弃」；代码里检测到 `discarded` 会先 reload。
- 不识别「你正在看的那个会话」。要追加到当前会话，把 `qui.ini` 里 `Mode=new` 改成 `Mode=current`。
- 扩展没有远程代码，全部逻辑在本地文件里，可自行审阅。

## 踩过的三个坑（2026-10-22 实测记录）

### 坑 1：DSH 在后台时，投递从 1 秒变成 30 秒

**现象**：按 Alt+Q 发送后，必须切回 DSH 界面才会“生效”。

**根因**：Chrome 把隐藏标签页的 `setTimeout` 钳制到约 1 秒一次。早期版本找输入框用
`30 次 × sleep(100ms)` 轮询 → 后台状态下变成 30 秒。

**实测**：同一场景下延迟 17 / 27 / 32 秒；内容没丢，只是慢。

**解法**：所有 DOM 等待改用 `MutationObserver`（不受定时器节流影响），
`setTimeout` 只作兜底。修复后同场景 **1 秒内**完成。

> **凡是「等页面变化」的地方，一律不准用短间隔 setTimeout 轮询。**

### 坑 2：浮层里按回车没反应

**现象**：Alt+Q 弹出浮层，打字有显示，按回车和 Esc 都没反应。

**根因**：焦点只落在窗体上，没落到里面的 TextBox。`KeyDown` 处理器根本收不到消息
（日志里连一行都没有）。

**解法**：`Native.SetFocus(tb.Handle)` 直接把原生焦点给输入框；
键盘处理改到 `ProcessCmdKey`（比 `KeyDown` 早，也绕得开输入法候选框）。

### 坑 3：改了扩展代码，浏览器不会自动用新的

**现象**：磁盘上的代码改了，运行行为还是旧的。

**解法**：`chrome://extensions` 点该扩展的**刷新图标**才算生效。
**刷新扩展 ≠ 刷新页面** —— 页面里的内容脚本是另一份，需要 F5 才会换。

**已加自愈**：background 会 PING 内容脚本比对版本号，不一致就
`chrome.scripting.executeScript` 主动注入最新版；content.js 用「认领标记」
让旧的那份闭嘴。所以正常情况下 **只需刷新扩展，不必刷新页面**。

> 排查用：`http://127.0.0.1:47321/health` 的 `client` 字段显示扩展版本号，
> `lastError` 显示最近一次失败原因。

## 失败与重试（v1.1.0 起）

失败分两类，**只重试安全的那一类**——否则同一句话会被发两遍。

| 失败 | 重试？ | 为什么 | 后果 |
|---|---|---|---|
| `E_NO_COMPOSER` 找不到输入框 | ✅ 最多 3 次 | 页面上没留下任何痕迹 | 重试失败才丢 |
| `E_FILL` 填不进去 | ✅ 最多 3 次 | 内容没进输入框 | 重试失败才丢 |
| 页面超时没回应 | ✅ 最多 3 次 | 可能只是标签页被节流 | 重试失败才丢 |
| `E_SEND` 发送没成功 | ✅ 最多 3 次 | 发送前会二次核对，避免重发 | 重试失败才丢 |
| `E_SEND_KEPT` 文字还在输入框里 | ❌ **不重试** | 再填一次会把同一句话叠两遍 | 文字留着，切过去按回车即可 |

**重试节奏**：第 1 次失败等 1.2 秒，第 2 次失败等 2.5 秒；超时上限第一次 30 秒、重试 15 秒。
最坏情况（连挂三次）约 65 秒后放弃并记录到 `lastError`。

**「发送成功」怎么判定**：不能只看输入框清空——那可能是被别的东西清掉的。现在要两个条件同时成立：

1. 输入框里已经没有这段文字
2. 页面里能找得到这段文字（说明消息气泡真的出现了）

只要有一条不满足，就判定没发出去，继续走重试或报告失败。
